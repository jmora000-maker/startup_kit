## 1.1 SOW references are not always stories

ARC's SOW identifies its work by story IDs (`HS-####`). That is one case, not the norm. Other SOWs number their deliverables ("Deliverable 3.2", "D4"), cite only sections or clauses ("Section 4.2", "Exhibit B §3"), use a task or WBS code, or have no identifiers at all. The design must work in every case and must never require story IDs.

**SOW work item.** Every place this spec or v4 and v5 say "SOW story" now means **SOW work item**: the smallest unit of contracted scope that the SOW itself identifies or lists. Each work item has:

- **Reference**: the SOW's own identifier, or a synthetic one when the SOW has none.
- **Reference kind**: `Story ID`, `Deliverable number`, `Task or WBS code`, `Section`, or `Synthetic`.
- **Title**: the work item's name as the SOW gives it.
- **Phase or milestone**.
- **Owner**: Toptal or Client.
- **Type**: Build, Integration, Test, Certification, Analysis, or Documentation, when it can be determined.
- **Fingerprint**: a normalized-token signature of the title (the A2 tokenizer, sorted unique tokens), used to match the same item across runs when it has no SOW identifier.

**Reference detection.** Replace the hard-coded `\bHS-\d{3,5}\b` with a configurable, ordered list `SOW_REFERENCE_PATTERNS` in `src/config.py`. The first pattern that matches a work item sets its reference kind.

| Kind | Default pattern (case-insensitive) |
| --- | --- |
| Story ID | `\b[A-Z][A-Z0-9]{1,9}-\d{2,6}\b`, excluding this tool's own prefixes (`DEL`, `WP`, `RSK`, `ISS`, `DEP`, `ASM`, `AMB`, `Q`, `M`, `MS`, `COM`, `DEC`, `ACT`, `ACT-REQ`, `RAID`, `G01`) |
| Deliverable number | `\bDeliverable\s+\d+(?:\.\d+)*\b` and `\bD\d+(?:\.\d+)*\b` |
| Task or WBS code | `\b(?:Task\|WBS)\s+\d+(?:\.\d+)*\b` |
| Section | `\b(?:Section\|Clause\|§)\s*\d+(?:\.\d+)*\b` |

In the table, `\|` is Markdown escaping; the actual patterns use a plain `|`. Teams can extend the list for a client's own ID format without code changes.

**When the SOW has no identifiers**, the catalogue is built from the SOW's own list of contracted scope: its deliverables list, work output table, or the "Contracted Deliverables" entries in the SOW Interpretation Summary.

- Each listed item becomes a work item with reference kind `Synthetic`.
- Its reference is `SOW-{phase code or milestone ID}-{nn}`, numbered in document order within the phase (for example `SOW-P2a-03`, or `SOW-M1-01` when there are no phase codes).
- When the SOW has neither phases nor milestones, the reference is `SOW-{nn}`.

**What changes when there are no SOW identifiers**

| Feature | With SOW identifiers | Without (synthetic only) |
| --- | --- | --- |
| Workbook column (v5 A22) | Renamed **SOW References**: lists the SOW's identifiers | Lists the synthetic references, with the note `Synthetic reference - SOW has no item IDs` on the Schedule title row 4 |
| Core delivery tasks (v5 A21 option 2) | `{verb} {reference}: {title}` | Same, using the synthetic reference and the item title. Without a title, use the template core task |
| RAID-to-deliverable links (v4 A17) | Index of SOW identifiers found in RAID text | SOW identifiers are rarely cited, so links come only from Section or Deliverable-number references, plus the v3 A4 rules. Missing links are expected, not a defect. |
| Contract Reference (A28) | Citation, plus identifiers and sections | Citation and sections only |
| Traceability self-check | `SOW references: n in baseline, n in WBS, missing: ...` | Same, counting synthetic references, with the line `SOW has no item IDs; synthetic references used` |
| Cross-run stability (A31, B4) | Compare by reference | Compare by fingerprint: items match across runs when token Jaccard is at least 0.6. Report unmatched items as instability. |
| No contracted scope list at all | — | The catalogue is empty. Fall back to the v2 and v3 deliverable-based behavior (deliverables from extraction; template tasks). Log a WARNING (not an ERROR, see B1). Self-check line: `No SOW work items identified`. |

**Naming in this spec.** Wherever sections A21 to A31 and B1 to B4 below say "story", read "SOW work item". Wherever they say "story ID", read "SOW reference". ARC-specific expectations (35 stories, `HS-####`) remain correct for the ARC fixtures only.

# Part A: Workbook changes

## A28. General citation parser (amends v3 A7 and v4 A16)

Recognize a leading citation in `conflicting_clauses` in any of these forms, tried in order:

1. `[V#] <document>.<ext>, <ref>: <text>` (v3 A7).
2. `<Exhibit|Schedule|Appendix|Attachment|Annex> <id>[, <section words>]: <text>`, for example `Exhibit A, Client Responsibilities: ...` or `Exhibit A: ...`.
3. `<document>.<ext>[, <ref>]: <text>`.

Contract Reference = the matched citation (for example `Exhibit A, Client Responsibilities`), then ` | Stories: ...` and ` | Sections: ...` from the v4 A16 extraction when present. Description keeps the text after the colon, prefixed by the category.

`Not cited` is used only when none of these, nor any story or section reference, is found. For ARC run 4, all 15 ambiguities get a reference.

## A29. Second-pass work package assignment

After the v4 A14 assignment, attach each still-unassigned work package to a deliverable in the same milestone that has no work package yet, when:

- both share a distinctive token (IDF across that milestone's deliverable names of at least `ln(2)`, meaning the token appears in at most half of them), and
- the work package has no better candidate.

If no deliverable qualifies, the work package stays in `Other {workstream} work`. Basis on the task: `Backlog match (second pass)`. For ARC run 4, WP-10 attaches to DEL-12, and `Other P2b Application Surface work` disappears.

## A30. Multi-deliverable work packages

When a work package also scores at least 0.30 against other deliverables (anywhere, not only in its own milestone), keep its task under its best deliverable and add the note `Also covers {DEL-IDs}` there. Add the note `Covered by {WP-ID} ({best DEL-ID})` to each other deliverable's row. Those deliverables still get their own story or template core tasks.

## A31. Cross-run work item stability test

Freeze `arc_run4` from this run. Add `test_story_phase_stability.py`: for each SOW work item present in both `arc_run3` and `arc_run4` (matched by reference, or by fingerprint when synthetic), the Workbook must place it in the same milestone. Expected: all 35 identical. A difference fails the test and prints the story, both deliverables, and both milestones.

# Part B: Kit and Checklist changes

## B1. Make the story catalogue drive the backlog (fixes v5 B13)

1. Find why the catalogue did not drive the backlog in run 4: empty catalogue, or a fallback path taken. Fix it, and add a regression test reproducing it.
2. When the catalogue has at least one Toptal-owned story, the backlog is built from the catalogue. The LLM backlog is not used.
3. When the catalogue is empty because extraction failed even though the SOW lists contracted scope, log at ERROR, render the backlog with a single row `[CONFIRMATION REQUIRED: SOW work item catalogue empty]`, and add an exception to G01-03. When the SOW genuinely lists no scope items (section 1.1, last table row), log a WARNING, and build the backlog from the extracted deliverables with real parents. Never render work packages with blank parents.
4. Every work package carries a Parent Deliv, its SOW story ID, and an owner. The owner is `Toptal Delivery Team` when unassigned, not an action placeholder, because work package ownership is not a readiness control.

## B2. Evidence by story (fixes v5 B11)

1. The acceptance extraction returns evidence **per SOW work item** when the SOW states acceptance at that level (ARC: each Work Output row has its own criteria and evidence). When the SOW states acceptance only per deliverable or per milestone, keep the v5 B11 deliverable-level join.
2. A deliverable's evidence = the evidence of its stories, de-duplicated and joined with `; `.
3. When the extraction returns a group item covering several stories, assign it to **every** deliverable whose stories it covers, with the note `Shared evidence item covering {story IDs}`. One-to-one assignment applies only to name-similarity joins.

**Target for ARC:** 19 of 19 deliverables with evidence, and no deliverable holding evidence for a story it does not carry.

## B3. Concise review-window default (amends v5 B12)

When the SOW approval statement names a milestone acceptance review and gives no duration, use exactly `Not specified; reviewed at the end-of-milestone Acceptance Review`. Otherwise use the first sentence of the statement, truncated to 120 characters. Never paste the whole paragraph.

## B4. Stable deliverables from stories (replaces v5 B16)

Deliverables are derived deterministically from the work item catalogue (SOW identifiers or synthetic references, section 1.1), not chosen by the LLM. When the SOW itself lists deliverables, each SOW deliverable is one deliverable and this grouping rule is not needed:

1. Group Toptal-owned stories by phase, then by work type in this order: Build, Integration, Test, Certification, Analysis, Documentation. Work type comes from the story's type, and from its title keywords using the v2 7.3 table when the type is missing.
2. Within a phase and work type, split the group when the SOW's Work Output headings separate the stories. Otherwise keep one deliverable per group, with at most 5 stories per deliverable, splitting in story-ID order.
3. Number deliverables `DEL-01`, `DEL-02`, and so on by phase order, then work-type order, then lowest story ID.
4. Name each deliverable from the SOW Work Output heading when there is one. Otherwise name it from the joined story titles, shortened to 80 characters.
5. Keep the LLM's deliverable names only as `Deliverable.description` hints. They never change grouping or IDs.

**Acceptance check:** two extractions of the ARC SOW produce identical deliverable IDs, names, and work item sets. For a SOW without identifiers, two extractions produce the same deliverable count, and at least 90% of work items match by fingerprint.

## B5. M1 date question (third attempt; amends v5 B15)

Generate the "no committed external delivery date" question for every milestone whose external date is empty, whether or not it has a linked date action. Add a test with four undated milestones, M1 having a linked action, that expects four questions.

## B6. Finish the Fixed Bid guardrails

- Internal Escalation Thresholds becomes "Milestone slip > 3 days or acceptance rework beyond one cycle".
- Variance baseline and target become "Milestone acceptance on plan".
- Budget audit becomes "Milestone acceptance and Change Order log review".

No guardrail text for Fixed Bid may mention effort, rate, burn, or a percentage of budget.

## B7. G01-08 wording

Evidence = `{n} delivery talent roles listed; {m} named` (for ARC: `5 delivery talent roles listed; 0 named`). Status stays `In Progress` while `m < n`.
