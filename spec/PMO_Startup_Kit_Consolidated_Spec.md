## 0. Document control

**This document is the single source of truth.** It replaces every earlier spec. Move these files to `spec/archive/` and do not implement from them:

- `PMO_Startup_Toolkit_Workbook_Spec.md` (base)
- `PMO_Workbook_Delivery_Alignment_Spec.md` (v1)
- `PMO_Workbook_Delivery_Alignment_Spec_v2.md`
- `PMO_Workbook_Quality_and_Traceability_Spec_v3.md` to `..._v7.md`

**How it changes.** Future changes edit this document in place. A change adds, edits, or retires a requirement by ID, increments the Revision, and lists the change in section 18. Never add an amending document. A requirement ID is never reused.

**Status legend**

- `Done`: implemented in v0.5.5. Verify it with its test; do not re-implement it.
- `Pending`: not yet implemented, or implemented and failing review.
- `New`: introduced by this revision.

**Format of a requirement.** Each requirement has an ID, a statement, a status, and the test that proves it, written as `Test:` followed by the test file. A test may cover several requirements.

## 4. Extraction validation layer

A single module, `src/llm/validation.py`, runs after `BaselineAggregator` and before any document is generated. It returns a `ValidationReport` of findings. Each finding has an invariant ID, a severity (`repaired`, `warning`, or `error`), and a message.

| ID | Requirement | Status | Test |
| --- | --- | --- | --- |
| VAL-01 | **Milestones are reconciled to SOW gates.** The gate count comes from, in order: an explicit statement ("four sequential milestones", "N milestones") in decisions, assumptions, or the SOW Interpretation; the phases listed in approver decision rights or a per-milestone communications item; or the distinct phase codes in the contracted deliverables. When more milestones were extracted than there are gates, restatements (`acceptance\s+review\|sign-?off\|gating\s+the\s+start`) merge into their gate, and within-phase checkpoints move to `baseline.interim_checkpoints` (`CP-NN`). Gates are renumbered `M1`–`MN` in delivery order. Each renumbered gate keeps its extracted ID, and any merged IDs, as provenance (for example `extracted_ids: ["M3", "M4"]`). The Kit, Checklist, and Workbook all use the renumbered IDs. Provenance appears in the Workbook Notes as `Extracted as M3; includes M4 (acceptance review and sign-off)`. RAID rows and questions that name an extracted ID are relinked to the renumbered gate, with the note `Refers to extracted M4 (now M2)`. When fewer milestones were extracted than there are gates, record a `warning` and add an open question naming the missing phase. | Done (verified Rev 7 round) | `test_validation_layer.py`, `test_gate_reconciliation.py` |
| VAL-02 | **Work packages are built after deliverables, from the work item catalogue (REF-03).** Every work package has an existing parent deliverable, a SOW reference that matches `SOW_REFERENCE_PATTERNS` or is synthetic, an owner that is not an action placeholder (default `Toptal Delivery Team`), and `linked_milestones` set to the gate of **its own work item's phase**, never to a default or first gate. Phase names in the reference field are rejected. Invalid LLM work packages are discarded and rebuilt from the catalogue. If the catalogue is empty even though the SOW lists scope, record an `error`. | Done (verified Rev 2 run, Appendix F) | `test_validation_layer.py`, `test_backlog_recorded.py` |
| VAL-03 | **IDs are unique.** Decisions, deliverables, work packages, and milestones are renumbered sequentially when IDs repeat or equal a model default. Linked references are updated. | Done for decisions; generalize | `test_validation_layer.py` |
| VAL-04 | **No default-filled links.** `linked_milestone` and `linked_deliverable` on dependencies and assumptions are set only when the item text names the target. They are never copied from the first milestone or deliverable. | Done | `test_validation_layer.py` |

## 15B. Pre-Generation Human Review

**Purpose.** A new, opt-in checkpoint in the live generation pipeline (`main.py`, not the test corpus). With `--review`, the pipeline extracts and validates exactly as today, then pauses before any document is written. A person reviews a fixed set of high-value extracted facts in a small Streamlit app, confirms or corrects them, and only then does generation proceed. This is a different system from QA-01 to QA-12's oracle and snapshot review, which governs the recorded test corpus; this section governs real, live engagements. The two systems share only the `StartupKitBaseline` model (HTL-11).

Every fact category in HTL-06 was chosen because it caused a real, previously-found defect in this project (wrong phase assignment, a fabricated award date, an expanded task name, and so on) — this is deliberately a short, targeted list, not an attempt to have a person re-read everything the LLM extracted. A later revision extends it only when a real defect shows it is needed, the same standard every other requirement in this spec has been held to.

## Appendix Q: Pre-Generation Human Review design (section 15B)

**Why this exists, and why it is separate from the oracle/snapshot system.** QA-01 to QA-12 govern a small, fixed, recorded test corpus — SOWs that will never change, reviewed once by a person and then checked automatically forever after. Section 15B governs the opposite case: a real engagement, run once, whose facts have never been seen before and will never recur exactly. The oracle system cannot help here, because there is no pre-written ground truth for a brand-new SOW. What this system borrows from the oracle system is the *principle*, not the mechanism: a person, not the AI, is the final word on whether an extracted fact is true, and that person's decision is recorded, not inferred.

## Appendix R: Storage abstraction and cloud deployment design (HTL-13 to HTL-15)

**Why this exists.** Appendix Q's design assumed one person, one machine, local disk. Three things changed that: other people need to use this, it needs to run on Cloud Run (whose instances do not share a local filesystem and get recycled), and local development must keep working exactly as before, unaffected by any of that. The fix is the same one the rest of this codebase already uses for an analogous problem — `ILLMClient` lets `LangChainLLMClient`, `MockLLMClient`, and `CachingLLMClient` all stand in for each other; `ReviewStorage` does the same for "where does a paused run live."

**R.1 The interface (worked sketch, not a mandated implementation)**

```python
class ReviewStorage(ABC):
    def create_run(self, run_id: str, baseline: dict, validation_report: dict) -> None: ...
    def get_run(self, run_id: str) -> ReviewRun: ...
    def list_runs(self, state: Optional[str] = None) -> list[ReviewRunSummary]: ...
    def update_status(self, run_id: str, new_state: str, if_state: Optional[str] = None) -> None:
        """Raises if if_state is given and does not match the run's current state --
        this is what makes a single Approve click uncontested (HTL-09)."""
    def save_corrected_baseline(self, run_id: str, baseline: dict, audit: dict) -> None: ...
    def put_generated_files(self, run_id: str, file_paths: list[Path]) -> dict[str, str]:
        """Returns {filename: download_reference}; a local path for the local backend,
        a signed URL for the cloud backend."""
```

**R.2 Why `pytest` must never see the cloud backend.** This is the same discipline `LLM_CACHE_MODE` already enforces for live API calls — a test suite that could silently touch a real cloud project is worse than one that fails loudly when misconfigured. `REVIEW_STORAGE_BACKEND` defaults to `local`; test configuration pins it to `local` explicitly rather than trusting the default, exactly as replay-mode tests pin `LLM_CACHE_MODE` rather than trusting whatever a developer's shell happens to have set.

**R.3 Why IAM-only access does not weaken HTL-09.** `HTL-09` requires that approval only ever happen from a real click in a live browser session, never from a script or an automated caller. Restricting *who can open the app at all* (Cloud Run IAM) is a different, additive layer: it narrows who can even reach the point of clicking Approve, but the click itself is still the only path to `update_status`'s `if_state`-guarded transition, for every person who is let in. Replacing IAM later with an in-app login (per the open question in Appendix Q) would add a second, independent layer on top of this one, not replace it.

**R.4 What is explicitly deferred, and why.** Per the agreed build order (section 17), the cloud backend and deployment (`HTL-14`, `HTL-15`) are the last things built, not the first — everything through `HTL-12` is proven against the local backend alone. This mirrors how every other feature in this project has been built: the riskiest, most novel piece (here, the review screen itself) proven in the smallest possible harness before any surrounding infrastructure is added.

## Appendix U: The lost award-date conflict warning (the basis for Revision 22)

**Found while investigating, not while building.** This gap surfaced from a direct question asked alongside the `HTL-18` audit, not from the audit itself: does the warning `extract_stated_award_date` produces when two SOW dates disagree actually reach anything a reviewer would see?

**The answer, traced precisely.** `orchestrator.py:157` captures the warning as `date_warning` and never references it again; only the resolved date and its provenance flag continue into aggregation. The warning's only effect, anywhere, is a `logger.warning` call inside `date_extractor.py` itself — console or log output, not part of any generated artifact. `record_fixtures.py` discards it the same way, with an explicit `_`. No other validation rule fills the gap: `VAL-05`/`INV-18` (`validate_award_date`) is a different check, with a different trigger (it fires when no stated date exists at all, or one exists without provenance) and a different message (it only ever says "not specified" or "no stated provenance," never naming a second, conflicting date). Because `extract_stated_award_date` already resolves the conflict and returns a date with provenance `stated`, `VAL-05` does not fire in the conflict case at all.

**Net effect.** When a real SOW's preamble and its Section 3 give different dates, the tool quietly picks the preamble date (per `VAL-11`'s tie-break rule, confirmed correct in Revision 20) and nothing anywhere — no open question, no validation finding, no Kit or Checklist text — tells a reviewer that a conflict existed or that a choice was made. This was never caught by the `arc_application_implementation` fixture, because its two real dates agreed; only a synthetic test exercised the disagreement path at all, and that test checks the function's return value directly, never `orchestrator.run()`'s actual behavior.

**The fix, now specified (`VAL-11`, `INV-38`).** `orchestrator.run()` must carry the warning into the baseline as a real open question or validation finding, naming both dates and which one was preferred, the same way every other validation concern in this system already reaches a generated artifact rather than only a log stream. `INV-38` checks that this never silently vanishes again.

**Confirmed in a real generated document, not just internally.** A real, non-mocked `DocxGenerator` run against a SOW with two conflicting dates (`"This SOW becomes effective on October 7, 2026"` / `"Section 3: Estimated Start Date October 14, 2026"`) produces a Checklist whose `Actionable Questions & Open Clarifications` table contains, verbatim:

```text

     from estimated start date (2026-10-14 from 'Estimated Start Date October 14, 2026'). Governing preamble
     effective date selected per VAL-11. | Delivery Manager / Client Sponsor | Open
```

This is exactly `INV-38`'s finding message, naming both dates and which one was preferred, in a document a reviewer would actually open.

**A related, broader gap found along the way (`KIT-13`).** The Kit's own `Ambiguities & Clarification Notes` row does not show this, or any `open_questions` content: its text is sourced entirely from a different field (`sow_interpretation.ambiguity_notes`), and `open_questions` is read only as a boolean styling flag. This holds for every entry in `open_questions`, not only the `INV-38` case — a reviewer reading only the Kit has no way to tell whether zero, one, or many questions are open. This is not a violation of anything previously required (no requirement asked the row to reflect `open_questions`), so it is logged as new, deferred work (`KIT-13`), not treated as a defect in this fix. The Checklist remains the confirmed, canonical, complete place this content appears.

## Appendix W: Connecting Generate and Fact Review (the basis for Revision 27)

**What hands-on testing found.** Four observations from actually using the app, all tracing to one cause: Generate (`HTL-17`) and Fact Review (`HTL-06`/`HTL-07`) were built as two separately-verified halves on purpose -- Fact Review first, standalone, against one fixed fixture, to prove the hardest and most novel piece in isolation; Generate second, straight through with no pause, since the queue/state-machine/approval plumbing connecting the two (`HTL-01` through `HTL-13`) was explicitly deferred until each half worked on its own. That plumbing is what was missing:

1. Contract Type, Governance Tier, and the three named roles showed different values on the two screens, because Generate's copies are fresh defaults for a run that has not happened yet, and Fact Review's are extracted values from an unrelated, already-completed run -- they were never the same run.
2. Fact Review should come before final generation, which is exactly the intended design (extract, pause, review, approve, generate) that had not yet been built.
3. The same fields appearing editable in two places, with no link between them, looked like carelessness rather than two distinct moments in one process.
4. The specific mismatches named (Contract Type, Governance Tier, PMO Lead, Delivery Lead, Talent PM) are precisely the fields `HTL-06`'s `project_identity` and `named_roles` categories already cover -- confirming Fact Review was always the intended place these get corrected, just not yet connected to a real Generate run.

**Two decisions made, directly, not guessed at:**

| Question | Decision |
| --- | --- |
| Should review-before-finalizing be required or optional? | Default on, with an explicit opt-out toggle for a fast/quick run -- not mandatory, not silently skipped. |
| What happens to the five identity/role fields on Generate? | They become the Fact Review screen's responsibility entirely when review is on: read-only on Generate, editable only on Fact Review, whose corrected value is what actually reaches the final documents. When review is off, they revert to Generate's original, directly-editable, pre-extraction-hint behavior -- the two states never overlap. |

**Why the CLI's `--review` default (`HTL-01`, off) and the app's new default (`HTL-29`, on) are allowed to differ.** They are the same underlying mechanism (`HTL-02`'s split point) serving two different audiences with different default expectations: the CLI is frequently run non-interactively, in scripts and automation, where pausing by default would break existing usage; the app is a person sitting at a browser, for whom pausing to confirm what was extracted is the safer, more useful default, with a clear way to skip it when it is not wanted.


## Appendix X: A real production failure, and the bug it found (the basis for Revision 28)

**How this was found.** Not by investigation first -- by a real user report ("the app did not fall back to OpenAI when the API reached its usage limit") that a prior investigation's isolated, mocked reproduction could not reconcile. The user then supplied the actual raw log from the real failure, which told a different and more precise story than the mocked test had.

**What the log actually shows, quoted directly.**

The primary failure was never a rate limit. It was a workspace-level usage cap:
```text
Anthropic text generation failed (AnthropicInvalidRequestError): Error code: 400 - {'type': 'error', 'error':
{'type': 'invalid_request_error', 'message': 'You have reached your specified workspace API usage limits.
You will regain access on 2026-11-01 at 00:00 UTC.'}, ...}
```
This repeats once per concurrent domain-extraction call (the 12-pass thread pool), each with its own `request_id`, confirming the workspace cap applies account-wide, not per-call.

The code did attempt the Anthropic-to-OpenAI fallback -- proven by the exception type changing to an OpenAI-origin error:
```text
Anthropic schema-instructed JSON extraction failed (OpenAIInvalidRequestError): Error code: 400 - {'error':
{'message': 'max_tokens is too large: 32768. This model supports at most 16384 completion tokens, whereas
you provided 32768.', 'type': 'invalid_request_error', 'param': 'max_tokens', 'code': 'invalid_value'}}
```
Every fallback tier in `generate_structured` (native structured output, prompt-based extraction, a second structured attempt, the final parser-based attempt) independently reuses the same `max_tokens` value, so every one of them failed this same way, in sequence, logged repeatedly in the real trace.

**Root cause.** `MAX_TOKENS=32768` was set earlier in this project specifically to fix an Anthropic truncation problem (a real fix, correct for Anthropic, which supports that ceiling). Nobody checked, at the time, whether that same value would remain valid when the code falls back to a different provider. `gpt-4o`'s hard ceiling is 16384. The fallback mechanism, which has existed and worked for other failure types throughout this project, was never actually broken as a *mechanism* -- it was invoked correctly, every time -- but it was handed an invalid parameter for the provider it was falling back to, so it failed before ever reaching OpenAI's own rate limit or quota logic.

**Why the earlier investigation's reproduction missed this.** That reproduction used a single, isolated, fully mocked call, where `_openai_chat_model.invoke` was a `MagicMock` returning a canned value -- it never made a real call with a real, invalid parameter, so it could not have caught a parameter-validity bug. The lesson carried forward: a mocked unit reproduction proves a code *path* exists; it does not prove that path succeeds against a real provider's real constraints.

**What this means for `LLM-02`'s reverse direction.** The investigation that found the missing OpenAI-to-Anthropic fallback (no reverse direction exists at all when OpenAI is configured as primary) remains correct and unaffected by this finding -- that gap is real and separate from the `max_tokens` bug, and both need fixing.

**The fuller history behind `MAX_TOKENS=32768`.** It was raised, earlier in this project, specifically to fix an Anthropic truncation warning on one domain-extraction pass producing an unusually large response. At the time, the advice given alongside that fix was explicit: raising the ceiling is the right immediate fix, and *if the same underlying problem recurs*, the more durable fix is splitting that extraction pass into smaller, batched calls rather than continuing to raise the ceiling. The batching option was left deliberately deferred, conditioned on the problem recurring -- it was not forgotten, it was a real, scoped decision to wait and see.

This incident is arguably that recurrence, in a worse form: the same root cause (one pass needing an unusually large output budget) now broke the fallback mechanism entirely, rather than only truncating a response. `LLM-01`'s per-provider clamp is the correct fix regardless of whether batching ever happens -- it protects against any future provider or model ceiling mismatch, not just this one. Whether to also revisit the deferred batching fix, to reduce how large a single call's budget needs to be in the first place, is a separate decision, **Correction, after checking the real incident rather than only the test-fixture corpus.** The original, unconstrained truncation incident was confirmed (session transcript, 2026-09-30) to have hit Anthropic's `max_tokens` ceiling at exactly 16,384 and been cut off mid-payload -- meaning the true, complete response was longer than 16,384 tokens. That is also OpenAI's hard ceiling. So for that exact real SOW, `LLM-01`'s clamp (correctly limiting the *request* to a valid value) would not, by itself, have prevented the *response* from truncating again, just on the fallback provider instead of the original one -- a different failure mode than the "invalid request" bug `LLM-01` fixes, and one `LLM-03` did not originally cover. `LLM-03` is revised (Revision 30) to close this: both providers' own truncation signals must be checked, and a truncated response must never be silently treated as complete.

**What this means for the batching decision.** The 75-fixture corpus analysis (all comfortably under 16,384 tokens) is accurate but answers a narrower question than first assumed -- it shows today's recorded test fixtures are safe, not that every real SOW will be. The one real incident that started this whole investigation is direct evidence that a sufficiently dense real SOW can exceed even OpenAI's ceiling. With `LLM-01` and the corrected `LLM-03` in place, that case will now fail cleanly and visibly instead of silently returning corrupted data -- which closes the safety gap -- but it will still fail, for a SOW shaped like the original incident, unless the Scope Decomposition pass is batched into smaller calls. Whether to build that now is still the user's decision, made with this fuller picture rather than the fixture-only one.


**Root cause, confirmed against the actual regex.** Neither `PHASE_LABEL_REGEX` nor `WRAPPED_PHASE_LABEL_REGEX` matched any of these four strings -- both require a colon separating the phase title from a scope sentence, and GPT-4o's phrasing has none. Claude's known-correct phrasing for the same milestones, by contrast, always includes one: `"P1 Foundation accepted: micro-frontend shell, Azure AD/MSAL authentication ... are delivered and signed off."` The gap is a real difference in how the two models phrase the same fact, not a missing feature in GPT-4o's extraction and not a code regression.

**The fix, and why it is a real improvement rather than a second brittle pattern.** `Milestone.phase` is a structured field the extraction schema already asks every provider to populate directly (`src/core/models.py`: `phase: Optional[str] = Field(..., description="Delivery phase code for checkpoint/milestone (e.g. 'P3')")`). Checking GPT-4o's own raw extraction confirms it populated this field correctly (`"phase": "P1"`, `"P2a"`, `"P2b"`, `"P3"`) even though its free-text description didn't match the regex. Checking a known-good Claude-extracted fixture confirms Claude populates the identical field, identically reliably. `MS-02` is revised to check this structured field first, falling back to the existing text-pattern matching only when it is genuinely absent (a SOW with no stated phase codes at all) -- removing a colon-phrasing dependency that was always fragile, not patching around GPT-4o specifically.

**One thing checked and ruled out along the way.** The Fact Review screen showing correct phase names during the same session was not evidence the GPT-4o extraction worked -- `src/review_ui/facts.py`'s `FIXTURE_BASELINE_PATH` is hardcoded to the pre-recorded `arc_application_implementation` test fixture (Anthropic-extracted, long before this provider switch), confirmed by quoting the exact loading code. Fact Review has not yet been generalized to show a live run's own data (deferred, `HTL-13`); what it displayed was unrelated to this incident, not contradicting evidence.


## Appendix Z: `milestone.phase` is VAL-01's own field, not the extraction's (the basis for Revision 33)

**Caught before promotion, not after.** Reviewing Revision 32's proposed snapshot diffs ahead of promotion -- the same discipline applied to every snapshot change this session -- showed five fixtures' previously-correct workstream names silently corrupted: `mock_sow`'s `"Design & Architecture"` became `"G_1"`; `no_story_ids`'s `"Phase 1 Architecture and Core Foundation"` became `"G_1 Architecture and Core Foundation"`; `arc_genomics`'s `"P2a Services and Data"` became `"P2A Services and Data"`. None of this was accepted; it was traced to its real cause first.

**The actual mechanism, traced precisely.** A runtime print statement at Revision 32's new check confirmed `milestone.phase` equals `"G_1"`, `"G_2"`, `"G_3"` during real test execution, for fixtures whose `baseline.json` shows `phase: null` on disk. A code search found the source: `src/llm/validation.py`'s `reconcile_gates_and_checkpoints` (`VAL-01`) runs during baseline validation, before generation, and unconditionally overwrites every milestone's `phase` field for its own internal bookkeeping:

```python
if not has_phase_codes:
    for idx, ms in enumerate(baseline.milestones, start=1):
        phase_groups[f"G_{idx}"] = [ms]
    # ... phase_code = f"G_{idx}"; ms.phase = phase_code
else:
    phase_code = phase_m.group(1).upper()
    # ... ms.phase = phase_code
```

So `milestone.phase`, by the time any generator reads it, is never the raw extracted value -- it is always one of two things VAL-01 itself produced: a synthetic, sequential placeholder (`G_1`, `G_2`, ...) when no real phase code was ever stated, or an uppercased copy of a real code when one was. Revision 32's premise -- that both providers reliably populate this field, so it is safe to trust -- was correct about the moment of extraction (confirmed in Appendix Y) and wrong about what survives to the moment generation actually reads it, because a separate, pre-existing, correctly-functioning step overwrites it in between for a purpose unrelated to display.

**The fix (Revision 33).** `VAL-01` gains one new, additive field, `phase_display`, set alongside its existing `phase` assignment, never replacing it: when a real phase code was found, `phase_display` holds it with its original, as-stated casing; when none was found (the synthetic `G_N` case), `phase_display` is left unset. Every other consumer of `milestone.phase` throughout `validation.py`, `mapping.py`, `builder.py`, `docx_generator.py`, and `check_artifacts.py` is untouched -- this is additive, not a rename or a behavior change to `VAL-01` itself. `MS-02` is corrected to read `phase_display`, never `phase` directly, closing both corruptions at once: a synthetic placeholder is simply absent from `phase_display`, so step (1) correctly falls through to the existing fallback chain; a real code's original casing is preserved, so `P2a` never becomes `P2A`.

## Appendix BB: What `HTL-13` can enforce, and what only `HTL-09` can (the basis for Revision 36)

**Found while investigating `HTL-04`'s actual coverage**, not a planned design review. Checking the already-built `LocalReviewStorage` against all four of `HTL-04`'s clauses, with real code and reproduced test output:

- **Legal state values**: not enforced at the time of investigation (`update_status` accepted any string). Fixed directly in `local.py`.
- **A `rejected` run is terminal**: not enforced at the time of investigation -- reproduced directly: reject a run, then approve it with the correct `if_state="rejected"`, and the transition genuinely succeeded. Fixed directly in `local.py`.
- **A `generated` run excluded from the review queue by default**: `list_runs(state=None)` is, correctly, an unfiltered inspection tool, not an review-queue query -- a `generated` run appears in it, exactly as an unfiltered listing should. **The resolution.** `HTL-04`'s first three clauses are `HTL-13`'s responsibility and are now enforced there, confirmed by real tests. The fourth clause is `HTL-09`'s responsibility alone, at the app layer, exactly where the spec already placed it (`HTL-09`'s own text was never wrong about this) -- what this investigation adds is the explicit confirmation that storage was never meant to attempt it, so a future implementer does not mistake the absence of a caller check in `LocalReviewStorage` for a gap needing a storage-layer fix. When `HTL-09` is built, it must call `update_status` the same way any other caller would, never reimplementing the state-transition rules storage already owns.

## Appendix LL: HTL-33's first fix didn't hold in real use, and a follow-up attempt made things worse before the real fix landed (the basis for Revision 52)

**The automated regression test passed; the real app still failed.** After `HTL-33`'s first fix (Revision 51) was committed and pushed, the user tested it live, repeatedly, and the exact same symptom came back: Approve -> Generate documents -> the Save Review/Approve buttons reappeared instead of the download buttons. This happened on a genuinely fresh process (confirmed via `Get-Process` before each attempt, ruling out stale code) and, critically, in a single continuous session with *no page navigation at all* -- a simpler, more direct trigger than the original bug, which had specifically required a remount.

**Several investigation rounds were needed to find the real mechanism, and two of them were initially invalidated:**
- A reproduction using `AppTest` reported the fix working -- but it had not actually reproduced the real symptom (all 5 download buttons stayed present through its own test clicks), so its "confirmed root cause" was accepted prematurely and had to be challenged.
- An isolation test of `generate_approved_run` was run against the *wrong* stuck run's `baseline.json`, then (after the user supplied the correct real run ID) against the right one -- confirming the generation logic itself was never the problem.
- Temporary debug `print()` instrumentation was added directly into the live `app.py`, and the user ran the real, live, instrumented reproduction themselves multiple times -- this is what actually found the real mechanism, not any simulated test.

**The real mechanism, found via live instrumentation:** on one specific rerun, `current_selected` was captured holding the *formatted dropdown label* --

```text
current_selected='ARC Application Implementation (ARC_Application_Implementation_20261010_025820)'
```

-- instead of the bare `run_id`. Because the real `options` list only ever contains bare `run_id` strings, `resolve_select_index` correctly failed to find that label anywhere in it, fell back to `options[0]`, and silently switched the active run to an unrelated `pending_review` run. This fully explains every observed symptom: the vanished download buttons, the reappeared Save/Approve buttons, and `[DEBUG d] GENERATE HANDLER ENTERED` never printing (the click was real, but by the time its rerun executed, the "approved" run was no longer the one selected).

**The fix:** a `_canonical_run_id` helper now strips a label back to its embedded `run_id` at every read, `on_change`, and write site touching the persisted selection; `resolve_select_index` was also hardened to recognize a `run_id` embedded inside a label. This was confirmed working via the user's own live, repeated testing -- including the full real sequence (approve, generate, two real downloads, navigate away to Generate/Re-ingest, navigate back) -- not simulation alone, given how many times `AppTest` had already disagreed with real behavior on this exact bug tonight.

**A follow-up attempt made things worse, and was caught and reverted immediately.** A real, confirmed-harmless Streamlit internal warning remained (`"...created with a default value but also had its value set via the Session State API"`), and an attempt was made to silence it by conditionally passing `index=None` to the selectbox once its key already existed in `st.session_state`. This caused a serious new regression: the entire Fact Review page collapsed to just its title and the dropdown, because `st.selectbox` returning `None` on that path silently tripped the page's own `if not selected_run_id: return` early-exit guard, skipping every category field and every button. The user caught this immediately on their next live test ("terrible: ... only this remained on the page") and the change was reverted in the same session, restoring the known-working `index=select_index` behavior. The warning itself remains, confirmed cosmetic and non-blocking, deliberately left alone rather than risk a third attempt this late in the session.

**Separately, the user raised a related but distinct UX observation (`HTL-35`):** the Generate documents button has no disabled or in-progress state while generation is actually running, so nothing currently prevents a second click mid-generation, and there is no visible feedback that real work is happening during that window.


## Appendix MM: HTL-35's fix needed a genuine two-phase rerun, found only by deliberately trying to break it live (the basis for Revision 54)

**The first fix pass was structurally correct but invisible.** Binding `disabled=gen_is_running` to the button looked right in the diff and passed every automated test, but the user's own live test immediately exposed the real gap: the button never actually looked disabled during the run at all. The mechanism is a direct consequence of Streamlit's synchronous, single-pass execution model -- setting a session-state flag and then calling the real, long-running pipeline *within that same script pass* never gives the browser a chance to receive an updated (disabled) button before the whole pass finishes. The disabled state was real in memory the whole time; it just never reached the screen until it was too late to matter.

**The user's own accidental second click then directly tested the one real risk this posed:** clicking Generate a second time while the first was still running interrupted the in-progress pipeline mid-way. This was checked directly against the real filesystem rather than assumed safe -- `review_queue/` is only ever written once, atomically, as the final step after validation completes, so an interruption during the long extraction phase that precedes it leaves nothing behind at all. Confirmed real and harmless, not just plausible.

**The actual fix required a genuine two-phase pattern** -- set the flag and call `st.rerun()` immediately, with the real work deferred to the next pass, so the disabled button is what the browser receives first. This is a standard, well-documented Streamlit idiom for exactly this problem, not a novel workaround.

**A fourth, completely separate instance of the identical gap was then found live, by the user, on a different page entirely** -- Fact Review's own "Generate documents" button had no `disabled=` parameter at all, never having been addressed by `HTL-33`/`HTL-34`'s earlier work on that same button's selection-persistence bug. Fixed the same way, scoped per-run so it doesn't interfere with the run selector.

**Every one of these four fixes was confirmed only after the user deliberately tried to double-click each button immediately upon clicking it** -- the specific test automated tooling cannot perform, since `AppTest` has no concept of "what does the screen look like mid-call." This continues last night's pattern: automated tests necessary, never sufficient, for this category of timing-sensitive UI bug.


## Appendix NN: Fact Review's milestone phase correction had never actually worked, for any correction, not just this one (the basis for Revision 56)

**What started as `MAP-09`'s labeling fix surfaced a separate, independently serious bug.** While building the correction path for a milestone falling back to the new `"Unclassified"` placeholder, the investigation found that `src/review_ui/facts.py`'s `apply_corrections()` had only ever set `ms.phase = _phase_code(new)` -- extracting just a short code like `"P1"` -- and never set `ms.phase_display`, the field holding the reviewer's actual typed text. Meanwhile `src/generators/pmo_workbook/workstreams.py`'s `parse_milestone_phase()` only ever checked `milestone.phase_display`, never `milestone.phase`. The two fields had been silently disconnected since `MS-02` introduced `phase_display` -- meaning **any human correction to a milestone's phase or workstream in Fact Review, for any run, ever, was silently discarded** before reaching the generated Workbook, WBS, or Deck. The UI showed the correction as accepted; the real documents never reflected it.

**Confirmed and fixed with real before/after evidence.** `apply_corrections()` now sets `phase_display` to the reviewer's full input alongside the short `phase` code; `parse_milestone_phase()` now also falls back to a stored `phase` (when present and not one of `MS-10`'s internal `G_N` synthetic group codes, which must never be mistaken for a real phase label). A real test drove a full correction through the real pipeline -- `milestones.M1.phase` corrected to `"P1 Inception & Discovery"` in Fact Review, confirmed landing as `phase="P1"` / `phase_display="P1 Inception & Discovery"` on the corrected baseline, and confirmed appearing correctly in both the real generated Workbook's schedule row and the real Deck's Slide 3 table row -- the first time this specific correction path has been confirmed to work end to end.

**This was not a narrow side effect of `MAP-09`'s fallback-label fix.** It affected every milestone phase correction a reviewer could make, regardless of whether the milestone fell back to `"Unclassified"`, `"Build & Configuration"`, or anything else -- the connection between what a human typed and what the generators actually read was broken for all of them.


## Appendix OO: A real, controlled six-run comparison found a consistent extraction-quality gap between providers, independent of price tier (the basis for Revision 57)

**The investigation started from a real, concrete observation, not a general impression.** The user, after upgrading `OPENAI_MODEL` away from the legacy `gpt-4o` to a current OpenAI model (`gpt-6.1-sol`), directly compared its Fact Review output against Anthropic's and judged the quality roughly unchanged from the old `gpt-4o` era -- a real, first-hand finding worth taking seriously rather than dismissing. An initial assumption that this was a tier mismatch (comparing Anthropic's mid-tier Sonnet against an OpenAI budget tier) was checked and found wrong: `gpt-6.1-sol` and `claude-sonnet-5-5` are genuinely comparable, similarly priced current-generation models on both sides, confirmed via real web research on OpenAI's own model documentation before the comparison began.

**The comparison was run methodically, not off a single sample.** The real `ARC Genomics Platform Implementation` SOW (`Syngenta Crop Protection, LLC`) -- the same document whose correct structure (5 real milestones, correct client, correct Delivery Manager, 20 real deliverables) was already deeply familiar from tonight's other fixes -- was run through the full real pipeline three times with `LLM_PROVIDER=openai` and three times with `LLM_PROVIDER=anthropic`, with `fallback_domains` confirmed empty on every run (no cross-provider contamination) and each real `baseline.json` inspected directly.

**Real, concrete differences found, not stylistic ones:**
- **Factual hallucination:** 1 of 3 OpenAI runs fabricated a `"Cloud Infrastructure Architect"` role requiring AWS and Terraform skills in `talent_onboarding` -- directly contradicting that same run's own `exclusions` and `platform_environment_commitments` fields, which correctly state the client owns all platform infrastructure and Terraform. The other 2 OpenAI runs and all 3 Anthropic runs correctly listed only the real SOW-specified `Full-Stack Developer` and `QA Engineer` roles.
- **Self-consistency checking:** all 3 Anthropic runs independently noticed and flagged, in `confirmation_required_items`, that specific SOW work-item references cited in their own `contract_ambiguities` analysis (`HS-4781`, `HS-4827`, `HS-4831`) were never mapped to any actual baseline deliverable -- a real internal cross-check catching the model's own potential inconsistency. No OpenAI run performed this check at all.
- **Risk judgment versus placeholder text:** all 3 OpenAI runs assigned the literal string `"Not specified"` to every single RAID item's `severity` field, with no exception. All 3 Anthropic runs assigned real, varied judged values (`"High"`, `"Medium"`, `"Low"`) tied to specific reasoning in each item's `mitigation_or_response` field.
- **Cross-document consistency:** 2 of 3 Anthropic runs independently caught that the same underlying search-latency requirement was worded inconsistently across several separate SOW stories (some with percentiles, one without, differing measurement points) -- a genuine legal/contractual catch neither found in any OpenAI run nor in the first Anthropic run.
- **Completeness:** all 3 Anthropic runs included each milestone's real dollar fee amount from the SOW's own fee schedule in the milestone's own narrative description; no OpenAI run did.

**This is filed as an observational finding (`LLM-04`), not a code defect.** No part of the Startup Kit application is behaving incorrectly -- both providers are being called correctly, and the temperature-handling and fallback fixes from earlier tonight (`HTL-`-adjacent work) are confirmed working cleanly throughout this entire comparison. The finding is about model choice, not tooling, and is explicitly scoped to this one document type and this one real six-run sample -- a meaningful first signal, not a comprehensive benchmark.
